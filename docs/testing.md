# Testing

## How to run

```bash
createdb designmatch_test          # once
npm test                           # all tests (unit + integration)
npm run test:unit                  # Control-layer unit tests only, no database needed
npm run test:integration           # API tests against TEST_DATABASE_URL
npm run test:coverage              # with coverage report in coverage/ (fails below thresholds)
```

The integration tests rebuild the schema in `TEST_DATABASE_URL` before each file, so never point it at your real database.

## Test plan

| Level | Location | What it checks | Database |
|---|---|---|---|
| Unit - utilities and services | `tests/unit/utils.test.js` (UT-UTIL, UT-SEC, UT-RPT) | Date/period maths, input validation, password hashing, report formatting, CSV injection safety | No |
| Unit - Control classes | `tests/unit/controllers.test.js` (UT-AUTH, UT-ADM, UT-REG, UT-PRF, UT-IDP, UT-CO, UT-CUS, UT-MGT, UT-CON, UT-SRCH) | Business rules of every use case with Entity fakes injected through the constructor | No |
| Integration - API | `tests/integration/*.test.js` (IT-AUTH, IT-ADM, IT-REG, IT-PRF, IT-DES, IT-IDP, IT-ANA, IT-SRCH, IT-CUS, IT-MGT, IT-CAT, IT-RPT, IT-CON) | Full Boundary-Control-Entity chain over HTTP with Supertest and a real PostgreSQL test database: authentication, authorisation, validation, persistence, cascades, report figures | Yes |

Each test ID appears in the test name and in `docs/story-coverage.md`, so every story traces to its tests.
Scenarios covered for each feature: valid input, invalid input (400), boundary values (budget min = max,
leap years, week/month edges, 366-day limit), unauthorised (401), wrong role or not owner (403),
missing records (404) and duplicates/conflicts (409).

## Test data

- Integration fixtures (`tests/helpers/fixtures.js`): a small, known dataset (4 roles, 2 approved
  designers, 1 pending, 1 rejected, 4 IDPs) so assertions can use exact numbers.
- Demo/scale data (`npm run seed`, `scripts/generate_test_data.js`): Faker-generated records -
  208 accounts (101 customers, 102 designers: 81 approved, 15 pending, 6 rejected, 2 managers, 3 admins), 102 companies,
  about 120 certifications, 160 IDPs (19 hand-written plus 141 generated from the photo pools) with 332 photos,
  3,000 views, 450 favourites, 160 enquiries, 450 search logs and
  100 reports generated by the real report controllers. Lookup tables keep their controlled values.

## Evidence of test-driven development - what your team must record

The test suite in this repository is the end state. The marking scheme asks for evidence that tests
were written *before* the code, so the team should demonstrate the Red-Green-Refactor cycle on real
commits rather than presenting this suite as historical evidence. A practical way:

1. Pick a story per member (e.g. story 48 "search favourites").
2. On a branch, write or adapt the failing test first (e.g. `IT-CUS-05`), run `npm test -- -t "IT-CUS-05"`, screenshot the red result, commit with message `test: IT-CUS-05 search favourites (red)`.
3. Implement or adapt the code, rerun, screenshot green, commit `feat: search within favourites (green)`.
4. Refactor, rerun, commit `refactor: ...`.
5. Paste the screenshots and commit hashes into the report, and keep the CI run links.

Do not fabricate red/green screenshots or test output; record genuine runs.

## Results recorded by the developer

When the suite was prepared, it was executed against PostgreSQL 16 in an offline environment where
npm packages could not be installed, using minimal stand-ins for Jest, Supertest, Express and pg
(not included in the repository). Result: 141 tests, 141 passed (75 unit, 66 integration; 15 of them cover the admin console tools and the search filters), and about
98% of `src/` lines were executed (V8 line approximation). Run `npm run test:coverage` with the real
packages and use **that** output as the official evidence; branch coverage reported by Jest will be
lower than the line figure.
